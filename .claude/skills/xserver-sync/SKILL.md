# uto-usui.com の公開

公開は CI ではなく手元から行う。サーバーが SSH の接続元を絞っているので、GitHub Actions からは SSH できない（緩めない）。サーバー名・鍵などの手元の値は、コミットしない `.xserver.json` にある。このリポジトリは公開なので、手元のパスやサーバーの値をファイルやコミットに書かない。

**ふだんは手元の launchd が自動で出す**（`docs/xserver.md` の「自動デプロイ」）。master に入ったあと（PR のマージでも直接の push でも）は、このスキルで手で出さず、`~/Library/Logs/uto-usui/auto-deploy.log` と `~/.local/state/uto-usui-auto-deploy/last-sha` を見て、その sha が出たかを確かめて報告する。5 分たっても処理されていなければ `launchctl print gui/$UID/com.uto-usui.auto-deploy` で動いているかを見る。このスキルで手で出すのは、自動が止めたとき（確認が要る差分、CI が通っていない、CI の run がない）と、ユーザーに頼まれたときだけ。

自動デプロイは判断の表の 1 行目と 2 行目（スクリプトの判定）だけを見ている。3 行目（PR の変更から説明がつかない差分）は機械では判定できない。master からのビルドは決まった結果になるので、ふつうは起きない。

スクリプトは `scripts/xserver/cli.ts`、人向けの説明は `docs/xserver.md`。同期で消してはいけないサーバーだけのもの（`8180/` など）は、スクリプトの `EXCLUDES` が除外している。

## 流れ

1. **公開してよい状態かを確かめる。** どれか 1 つでも満たさなければ公開せず、理由を報告して終える。
   - `git switch master && git pull --ff-only` のあと、`git status --porcelain` が空で、`git rev-parse HEAD` と `git rev-parse origin/master` が一致する
   - そのコミットの CI が通っている: `gh run list --branch master --limit 1 --json headSha,conclusion,status` で、`headSha` が HEAD と同じで `conclusion` が `success`。CI が走らない変更（docs だけなど）で run がないときは、`pnpm verify` を手元で通す
   - `.env` に `PUBLIC_GA4_ID` がある（ないと deploy が止まる）
2. **ビルドして差分を取る。** `pnpm build && pnpm xserver:diff`。最後の「判定」と一覧を読む。
3. **判断する。** 下の表に当てはめる。
4. **進めるなら** `pnpm xserver:deploy --yes --no-build`（2 でビルドしたものをそのまま使う）。出力の最後の公開後の確認（✓ / ✖）とエラーログを読み、公開した URL（https://uto-usui.com/）と一緒に報告する。✖ があれば、原因を調べて報告する。直前の状態に戻すときは `pnpm xserver:rollback` で控えの名前を見て、ユーザーに確かめてから `pnpm xserver:rollback <名前> --yes`。

## 判断の基準

| 差分                                                                                                                                                            | 判断                                                                            |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| マージした PR の変更から説明がつく追加・更新と、前のビルドのハッシュ付きファイル（`_astro/*`）の削除だけ。スクリプトの判定が「確認なしで進めてよい」            | 確認なしで進める                                                                |
| ビルドが作らないファイルの削除（サーバーにだけ置いたもの）、`.htaccess` の変更、`index.html` が消える、ファイル数が大きく減る。スクリプトの判定が「確認が要る」 | 止めて、差分の一覧と理由を見せて確認を取る。了承をもらってから `--yes` で進める |
| PR の変更から説明がつかない追加・更新がある（触っていないページが変わるなど）                                                                                   | 止めて、何が変わるかを見せて確認を取る                                          |
| 1 の条件を満たしていない、ビルドやテストが落ちた                                                                                                                | 公開しない。理由を報告する                                                      |

`rsync --delete` は、ふつうは毎回ユーザーの確認が要る操作。このサイトでは、表の 1 行目に当たる差分なら確認なしで進めてよい、とユーザーが決めた（2026-10-25）。反映の前に必ずサーバー側に控えを取る（新しい 3 つを残す）ので、`pnpm xserver:rollback` で戻せる。

## やらないこと

- `EXCLUDES` を差分を通すために書き換えること。サーバーにだけ置くものが増えたときだけ足す（足すときはユーザーに確かめる）
- `public_html` の外（同じサーバーにある別のサイト）に触ること
- サーバーの設定の変更（SSH、接続元の制限、DNS、SSL）。必要になったらユーザーに確かめる
